# 01 需求分析：用状态栏宽度接管应用区

> 记录时间：2026-10-22　｜　基于 macOS 27.0.1（26A434），2056×1329 屏实测
> 本文只写"要什么"与"能不能做到"，实现细节见 README 与代码注释。

## 1. 需求

用一条自有的状态栏项（StatusX）接管菜单栏右侧的应用区：

1. StatusX 的状态项**固定宽度 310px**（设计值，2026-10-30 定案）。
2. 在这个宽度下，右侧还能放下 **12 个应用图标**。
3. ~~宽度在「310px ~ 占满应用区」之间可变~~（2026-10-30 停用：固定 310px，不参与其它项的排布）。
4. **不显示系统自带的 `<<` 按钮**。
5. 点 StatusX（或它右侧的自定义"隐藏/显示"图标）向下弹窗，列出所有菜单栏应用；
   点某一项时，让它的图标临时出现在该图标的位置，并执行对该应用图标的点击（弹出它自己的菜单）。

## 2. 实测基线（本文结论的全部依据）

| 量 | 实测值 | 说明 |
|---|---|---|
| 占位式宽项（第三方） | **310px** | 可变宽度文字项，会让整条栏持续漂移（两次采样间曾 +28px） |
| 应用区右边界 | 1829 | 控制中心 1841 左边 12px |
| 系统左界限 | 1185–1186 | 再往左就溢出 |
| 应用区容量 | **643px** | 1829 − 1186；随栏内已有项与内容宽度波动（实测 622–656） |
| StatusX 实际可用最大宽 | **598–629px** | 650 会把自己折进去；608 会漏出 1 个图标；
数值随栏内已有内容变化（其它项是否在栏、有没有录屏 HUD），不能写死 |
| 图标占位 | 约 26px/个 | 图标本体 18–38px + 2px 间隙 |

**"310px + 12 个图标"能否成立**：

```
310（StatusX 最小宽）+ 12 × 26（图标）= 622 ≤ 643   ✅ 成立，且不会溢出
310 + 12 × 26 + 24（`<<` 预留）      = 646 > 643   ❌ 多一项就溢出，`<<` 出现
```

即：**12 个图标只有在一个图标都不隐藏时放得下**；一旦要隐藏任何一项，`<<` 必然出现。

**实测复核**（`minWidth=310`、指定 12 个 26px 图标）：

```
StatusX 实际拿到 311px（x=899..1210），12 个图标全部可见
但 `<<` 依然出现在 x=1198 —— 因为另外 6 个图标没地方放、被折叠了
```
这一条最关键：**即使正好是"310px + 12 个图标"这个配置，`<<` 也去不掉**，
原因不是宽度算错，而是还有别的图标被折叠。

## 3. `<<` 按钮的三条硬约束（已实测，非推测）

1. **`<<` 存在 ⟺ 折叠组非空**。没有公开 API 控制它的显示；
   系统设置里也没有开关；24 项全可见时它不出现，折叠 1 项它立刻出现。
2. **折叠项的坐标是假的**。MenuBarAgent 的 `AssignCollapsedOverflowFramesPass` 会给折叠项
   伪造位置和宽度（曾返回 651px 的假宽度），所以"把某个折叠项拿出来"没有可用的坐标依据。
3. **折叠是单向的：能收进去，不能拖出来。** 两个方向都实测过：
   - **可见 → 折叠：可以。** 先把 StatusX 缩到 26px，再把目标图标 ⌘-拖到 StatusX **左边**（x=1140），
     它真的进了折叠组——实测 One Switch 落到 x=1154，与 iCopy/Snipaste/Mos 等折叠项同一锚点，
     `<<` 出现在 1162。这是"按 App 隐藏"的可行原语。
   - **折叠 → 可见：不可以。** 折叠项的 `AXPosition` 是系统伪造的假帧，⌘-拖拽抓不到它；
     拖拽落点若落在 StatusX 矩形**内部**，会被钳制回最左可见槽（同样的操作、StatusX 宽 381px 时，
     把 NeatDownloadManager 拖到 x=1200 就只落到 1574）。
   - 结论：**隐藏可控，显示回来自动发生（有空间时），但不能指定**。要让它重新出现只能靠"腾空间"
     （折叠别的项、或缩窄 StatusX），而不是把它拖出来。

## 4. 新方案逐条判定

| 需求条目 | 判定 | 原因 |
|---|---|---|
| 用 310px 做 StatusX 固定宽 | ✅ 已实现 | `Config.bandWidth`（旧配置键 `minWidth` 自动兼容） |
| 该宽度下显示 12 个图标 | ✅ 可以 | 622 ≤ 643，实测可容纳 |
| ~~宽度在 310px ~ 占满之间变化~~ | ❌ 2026-10-30 停用 | 改为固定 310px，不再搬动任何菜单栏项 |
| **不显示 `<<`** | ❌ 不可以 | 见 §3.1：只要有图标被折叠，`<<` 必出现 |
| 弹窗列出所有菜单栏应用 | ✅ 可以 | 已实现（可滚动清单） |
| **指定隐藏某个 App** | ✅ 可以 | 缩窄到 26px → ⌘-拖该图标到 StatusX 左边 → 它进折叠组（已实测） |
| **指定把某个 App 显示回来** | ❌ 不可以 | 折叠项坐标是假的、抓不到；只能靠腾空间让它自己弹出来，不能指定 |
| 点某项 → 它的图标临时替换"隐藏/显示"图标的位置 | ❌ 不可以（隐藏态下） | 需要把折叠项单独摆到某个位置，正是上一行的能力缺口 |
| 点某项 → 执行点击该图标 | ⚠️ 分情况 | 图标可见时：`AXPress` 直接可用（大多数成立，QQ 例外，已有回退）；图标处于折叠态：只能 `AXPress` 原地弹菜单，无法"先摆到某个位置再点" |

**结论：新方案的两条核心诉求（"隐藏其它应用"与"不显示 `<<`"）在公开 API 下互斥，不能同时成立。**
这不是实现程度问题，而是系统机制问题：`<<` 就是 macOS 表达"这里隐藏了图标"的唯一方式。

> 商业软件（Bartender、Ice）能做到"隐藏且无 `<<`"，是因为它们接管了整条菜单栏的渲染
> （截屏 + 自绘覆盖层 + 转发点击），不依赖系统的折叠组。那已经超出"只用公开 API"的范围。

## 5. 三条可选路线

| | A. 不隐藏（推荐用于"不要 `<<`"） | B. 真隐藏（现状） | C. 接管菜单栏渲染 |
|---|---|---|---|
| `<<` 是否出现 | **永不出现** | 必然出现 | 视觉上可以不出现 |
| 其它应用是否隐藏 | 否，12 个全可见 | 是，全部折进 `<<` | 是 |
| 弹窗列出所有图标 | 可以 | 可以 | 可以 |
| 点击弹窗项执行点击 | **可以直接点**（图标都可见，坐标真实） | `AXPress` 原地弹菜单；QQ 需回退 | 自绘，需转发 |
| 新增应用是否会挤爆 | 会（超容量就出现 `<<`） | 不会（自动折叠） | 不会 |
| 需要的权限 | 辅助功能 | 辅助功能 | 辅助功能 + 屏幕录制 |
| 系统升级风险 | 低 | 低 | **高**（27 已经让 Bartender 这类产品失效一次） |

- **A**：StatusX 固定 310px，右侧 12 个图标全可见，`<<` 不会出现；
  点 StatusX 弹窗列出全部菜单栏应用，点某项直接 `AXPress`（此时坐标真实、可靠）。
  代价：不隐藏任何图标，超过 12 个就会溢出。
- **B**：当前实现。所有第三方图标折进 `<<`，StatusX 629px；弹窗 + `AXPress` + 回退路径都已验证。
- **C**：另起炉灶，工作量与风险都是另一个量级，且与本项目"只走公开 API"的前提冲突。

## 5.1 顺序能否跨重启保持（2026-10-22 实测）

| 场景 | 结果 | 证据 |
|---|---|---|
| 只重启 StatusX 进程 | ✅ 保持 | 重排后杀进程重启，顺序仍在 |
| **系统重启** | ❌ **不保持** | 重启前拖成 `Karabiner → CommandX → DesktopTranslation → Moom(最右)`，重启后变成 `Karabiner → Moom → CommandX → DesktopTranslation`，Moom 从最右回到中间 |

原因（已查证）：⌘-拖拽**不会**回写对方 App 自己保存的 `NSStatusItem Preferred Position`
（Moom 拖前拖后都是 415）；系统侧也没有第三方的顺序存档
（`com.apple.controlcenter` 的 `MenuBarCustomizationState` 只有 Control Center 自己的模块，
`ByHost/...displayablemenuextras` 里 `displayableInfos` 为空）。
即顺序只活在当前登录会话的窗口服务器里。

**对策（已实现并验证）**：StatusX 自己记顺序。
`config.json` 的 `savedOrder` 保存"自身右侧可见项"的 bundle id 序列，启动时若发现不一致，
就用 ⌘-拖拽按记忆重排。实测：人为打乱后重启，顺序自动恢复。
重排必须**从左往右**摆——落到最左可见项左边就是隐藏区，会被直接折进去（第一次实现踩了这个坑）。

## 5.2 面板背景（正式版规格已记录）

代码位置：`Sources/StatusX/Panel.swift` 的 `FoldedPanel.init(background:)`；开关在
`config.json` 的 `panelBackground`。

| 值 | 效果 | 用途 |
|---|---|---|
| `popover` / 不写 | `NSVisualEffectView`，`material=.popover`、`blendingMode=.behindWindow`、`state=.active`、圆角 12 | **正式上线** |
| `white` | 纯白底（`NSColor.white`）+ 强制 `.aqua` 浅色外观、圆角 12 | 测试、截图 |

正式版的完整视觉参数（上线时照这个还原）：圆角 12、`hasShadow=true`、
面板宽 272、行高 26、行内边距 8、滚动手感沿用系统、底部固定操作栏。
白色模式额外强制 `.aqua`，否则深色模式下白底配白字会看不见。

## 5.3 面板视觉结构（2026-10-23）

参照同类菜单栏工具的面板改版，代码在 `Sources/StatusX/Panel.swift`（`CardView` / `FoldedPanel.rebuild`）。

自上而下：

1. **标题栏**（无卡片背景）：`StatusX` 加粗 14 + `v0.1.0` 灰色 11；右侧 `重新排布`、`退出 StatusX`
   两个无边框文字按钮（点「重新排布」= 手动重排一次并收起面板）。
2. **「菜单栏」卡片**：左上标题 13 加粗，右上大字 15 加粗显示当前宽度（如 `634 px`）；
   分隔线；下面三列指标（小标题 10.5 灰、数值 13 中黑）：`折叠` / `保留` / `合计`。
3. **「已折叠」卡片**：标题 + 右侧项数；下面是 App 列表（图标 16 + 名称 13，行高 26）。
   最多显示 14 行，超出可滚动，并在卡片底部提示「滚动查看其余 N 项」。

尺寸与间距：面板宽 340，面板内边距 12，卡片内边距 14，卡片圆角 10 + 0.5pt 细边，
卡片间距 10，行高 26。

背景两档（`config.json` 的 `panelBackground`）：

| 值 | 效果 | 用途 |
|---|---|---|
| `white` | 浅蓝白竖向渐变（`#E3F2FD` 附近 → 白）+ 强制 `.aqua` 浅色外观 | 测试、截图 |
| `popover` / 不写 | 系统毛玻璃（`.popover` + `.behindWindow` + `.active`） | 正式上线 |

已知坑：列表行高必须整倍数，否则最后一行会被视口切一半（已改成 `行数 × 26`）。

## 5.4 310px 带子里的内容（2026-10-30 定案）

- 带子里**不画** StatusX 自己的标识：只显示 CPU、内存、网络、硬盘、电池、风扇六个系统指标，可在设置「状态组件」页逐个开关。
- 电池要求：图标按电量比例填充内部空白；断电（用电池）时显示百分比数值，插电时不显示。
- 网络要求：按接口切换图标（Wi-Fi / 有线 / 蜂窝），蜂窝按速率近似 5G/4G/3G（macOS 没有公开的制式 API）。
- 风扇：系统没有公开 API，走 AppleSMC；读不到就不显示该组件。
- 图标与其它 App 的状态栏图标同尺寸（18pt）；文字两行：上数值、下名称。

2. 若选 A：StatusX 宽度固定 310，还是允许手动加宽（加宽就会挤掉右侧图标 → 又会出现 `<<`）。

## 6.1 拥挤时的启动死锁（2026-10-22 补记，已加自愈）

录屏时（菜单栏出现绿色胶囊 + 暂停/停止 + 计时，约 150px）叠加 StatusX 的 310px，整条栏会**超出容量**。
此时新建的 StatusX 会被系统**直接判定为放不下、生进折叠区**：它的 AX 坐标从此是假帧，
后续所有 ⌘-拖拽全部落空 —— 表现为"怎么点都没反应、宽度卡在 310 但人看不见"。

- 关掉录屏后立刻恢复：实测 598px 全隐藏，像素核对只有 `<<` + StatusX 图标 + 控制中心。
- 已加自愈循环：排在拖拽之前，若发现自己被折叠，就把可见项按宽度从大到小逐个收进折叠组
  （最多 16 次），直到自己浮出来。**该分支在本次复测中未被触发**（启动时就有空位），
  满栏场景尚未实测。

## 6.2 其它已知缺陷（与选题无关，需修）

- 当"保留项宽度"接近容量上限时（如 310 + 12 图标），StatusX 会紧贴保留块左端，
  系统的 `<<` 会落在 StatusX 矩形内部（实测 `<<` @1198，StatusX @899..1210），视觉上叠在一起。
  修法：落定后检查 `<<` 是否落在自己矩形内，若是则把宽度让出 `<<` 的宽度。
- **点折叠项的回退路径可能误伤别人的图标**（2026-10-23 实测）：AXPress 返回 `-25204` 时，
  程序会把自己缩到 26px 再按"真实坐标"去点。如果那一瞬坐标已经失效，点击会落到相邻项上。
  实测 AutoRaise 的状态项因此消失（`prefs` 里 `NSStatusItem VisibleCC Item-0` 被改写为 1），
  重启该 App 后才恢复。修法方向：回退前重新枚举并按 bundle id 精确匹配，拿不到就放弃（现在已经会放弃，
  但"拿到却错位"这一档还没有防护）。

## 7. 附：本机已验证的能力清单

- 枚举所有第三方状态栏项（`kAXExtrasMenuBarAttribute`），带 0.4s 超时防卡死
- 读取真实坐标 / 宽度；`AXPress` 弹出对方原生菜单（QQ 例外）
- ⌘-拖拽调整顺序（合成 `CGEvent`，需辅助功能权限）：**可见项之间任意重排，且重启后保持**
  （实测：Moom 1741 → 1786 → 1812 挪到最右，重启后顺序仍是 Karabiner / Command X / Desktop Translation / Moom）
  落点规则：插到落点位置上那一项的**前面**；落在最右项之后 → 追加到末尾
- 用 `NSStatusItem.length` 占位挤压，二分/搜索出最大可行宽度（629px）
- 判断"自己是否被折叠"：看 `<<` 的位置（在左≈1200 正常 / 跑到右侧≈1800 即被折）
- 像素级核对（截图 + 列区间扫描），用于绕开折叠项假坐标
